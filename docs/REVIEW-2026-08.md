# Code review — 2026-08 (P30.1)

**Packet P30.1, run 2026-08-21 on Fable 5.** A prioritised findings list over the whole tree,
read with `docs/RULES.md` (rev 24) open beside the code. The baseline was verified green before
reading began: **672 passed / 0 failed** (8m 34s).

**Method.** One main reviewer read the whole of `BurmesePoker.Domain` and
`scripts/drive-console.py` in full, plus every cross-project call site of the three identity
notions, the §7.1.1 table, and the multiplier constants. Four scoped sub-reviews — Server +
Presentation, Web, Console + Sim, and the test project — ran in parallel on the same model, each
against the same brief: the nine defect classes of `BUILD-PLAN.md` §5 P30.1, the rev-24 rules
facts, and the instruction to verify by reading rather than by grep. Every finding below names a
file and line, a severity, a class (1–9 from the packet, or *new*), and a triage. Line numbers
are against the tree at P29 (`ef2fffa`).

**Severity scale.** CRITICAL = rules mismatch / wrong behavior reachable in a shipped path ·
HIGH = real defect, narrow reach · MEDIUM = latent trap the next change springs · LOW = hygiene
with a concrete failure mode.

**Triage buckets.** This packet writes no code, so nothing is "fixed now": findings go to
**P30.2-fix** (small, safe, land alongside the conformance work), **P30.2-checklist** (a
conformance or coverage test to write), a **named later packet**, or **won't fix, because**.
Every finding is assigned.

## The headline, in three sentences

The engine's rules core is in excellent shape — the §7.1.1 table exists exactly once, every
identity-notion call site asks the right question, settlement and the feeding ban's release
semantics are correct, and no new rules question arose. The two defects that matter most are
**R1** (a human can throw a banned rank that was legal only as a declaring discard, then decline
to declare — §5.1 exception 2 is offered but never bound) and **R2/R3** (every journal written
since 2026-08-21 stamps itself rules rev 13, and a published P29 headline interval was computed
with the formula this codebase itself documents as wrong for that shape). The systematic hole is
**the fifth question**: the claim objection added by P28 is under-covered at every layer — no
test anywhere exercises `FallibleAgent.ObjectToClaim`, no connected fixture ever *allows* a
claim, the journal's `"objection"` line is covered by seed-luck, and two front-end translators
have default arms that would misrender a sixth question exactly as `JournalFormat.Name` once
mistranslated the fifth.

## Findings

### R1 — CRITICAL · class *new* — the exception-2 discard is not bound to the declaration that licenses it

`BurmesePoker.Domain/Play/FeedingBan.cs:130–142` (the exception-2 block of `LegalDiscards`) +
`BurmesePoker.Domain/Play/RoundEngine.cs:213` (discard first, `Declare` asked after).

§5.1 exception 2 permits a banned rank **only as the declaring discard**. `LegalDiscards` offers
a banned card whenever throwing it would *leave* a winning thirteen — and the engine then
discards it and only afterwards asks `agent.Declare(context)`, which may answer no. Both front
ends let a human decline (`SpectrePlayerAgent.cs:221` — `Confirm("Declare and end the round?")`;
`SeatAnswer.Declaration(false)` in the browser). The banned card then sits on the pile, takeable
by the protected seat — the exact gift §5.1 exists to forbid — and `RequireALegalDiscard` cannot
catch it, because it recomputes the same list. Bots are unaffected: every rung's `Declare` is
`=> true`, so no simulation figure moves. Reach: a human seat holding a closed rank in a 14-card
hand that wins after the throw — rare, and precisely a conformance case. **CONFIRMED.**

**Triage: P30.2-checklist + fix.** The fix shape: a discard that was legal *only* under
exception 2 commits the seat to the declaration — either the engine declares on the agent's
behalf (the discard *was* the declaration), or a declined declaration re-runs legality without
the exception and rejects the answer so the question stands. `RuleConformance` should assert *a
discard is never a closed rank unless the floor applied **or the round ended on it*** — the
build list's §5.1 item needs exactly this "or" spelled out.

### R2 — HIGH · class 5 — every journal written since 2026-08-21 stamps a false rules revision

`BurmesePoker.Domain/Play/GameJournal.cs:133` — `public const int CurrentRulesRevision = 13;`
while `RULES.md` is rev 24. The constant's own doc says *"Bump it when the rules document
changes in a way that changes play"*; P25 (win condition), P26 (money), P27 (feeding ban) and

journal the console or the harness has written since the rules sessions. The only test on it
(`Tests/Play/GameJournalTests.cs:214`) asserts the constant round-trips against itself, so no
test can see the staleness — class 3 in the same breath. **CONFIRMED.**

**Triage: P30.2-fix**, plus a guard: bind the constant to the rev parsed out of
`docs/RULES.md`'s header (P23's `StandingAnswerTests` idiom — the document and the code fail the
build when they disagree). Also add the bump to the `/poker` skill's Phase 6 checklist.

### R3 — HIGH · class *new* — a published P29 headline interval uses the independent formula on a within-cell margin

`BurmesePoker.Sim/Suite.cs:458` — the claim-permission **money** margin is
`Measurement.Difference(...NetPerRound, ...NetPerRound)`, an add-the-variances comparison of
`outs/refuse` and `outs/allow` **at the same table**. That is the within-cell case
`Measurement.Paired`'s own remarks (`Measurement.cs:170–177`) and the tournament footer document
as anti-conservative: money is zero-sum across a table, the arms' per-game nets are strongly
negatively correlated, and pairing widens the interval (~√2 on win rate; similar order here).
The same cell's *win-rate* margin is correctly paired (`Tournament.cs:509`), and `MoneySweep`
pairs all three of its within-cell margins (`MoneySweep.cs:306–308`) — this one row regressed
because `CellPlayer` keeps `WinRateByGame` and no `NetPerRoundByGame`. Published as
`claim.permission.money.refuse-over-allow = 0.020230 ± 0.177061` and quoted in `STRATEGY.md`
§12 as **"+0.02 ± 0.18"**; the true paired interval is wider (~±0.25). The null conclusion
survives — widening keeps a null a null — but the interval on a headline number is understated,
and a future re-run drifting near the understated boundary could promote a spurious
"separated". **CONFIRMED.**

**Triage: P30.2-fix** (a `NetPerRoundByGame` field on `CellPlayer`, `Measurement.Paired` at the
call site) **+ annotate `STRATEGY.md` §12** that the published ±0.18 is the unpaired formula.
The corrected row regenerates with **P31's already-planned full suite run** — do not spend 2¾
hours regenerating for this alone.
